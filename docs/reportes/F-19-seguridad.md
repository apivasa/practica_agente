# F-19 — Informe de seguridad
Veredicto: VERDE
Requiere cambiar alcance: no
Superficie nueva: ninguna. El cambio es lógica de `scripts/health/lib.js`. Se añaden `pickWorkflowCandidate` (pura, exportada) y `requiredStepProblem`. `maxDurationMin` valida las fechas con `parseApiTime`. `checkWorkflows` pide los jobs al candidato que se evalúa, y `listJobs` pagina con per_page=100 hasta 5 páginas. No hay endpoints, permisos, secretos, workflows ni dependencias nuevos. El modelo de amenazas no cambia.

Pruebas de seguridad añadidas: `tests/security/health-workflow-f19.test.js`, 127 casos, todos de la categoría 5 (automatizaciones):
- H-F18-01: 13 variantes hostiles de `run_started_at` / `updated_at` × las 3 reglas con `maxDurationMin`. Son estas: ausente, null, vacío, texto libre, número, objeto con `toString`, futura más allá de `FUTURE_SKEW_MIN`, ambas futuras, invertidas, sin zona y mes 13. Todas dan `fail`. Una duración real mayor que el máximo también da `fail`. El control positivo da `ok`.
- H-F18-02 (pura): 13 formas de jobs × las 3 reglas con `requiredStep` dan `fail`. Son estas: jobs vacíos, null o no lista; `run_id` ajeno, texto o null; mezcla de jobs propios y ajenos; paso renombrado o con otras mayúsculas; `steps` no lista; job sin steps; paso skipped, también en todos los jobs.
- `checkWorkflows`: se prueban cinco casos. (1) Un success viejo con el paso ejecutado va primero en el orden de la API y el candidato más reciente tiene el paso omitido: se piden los jobs del candidato y sale `fail`. (2) Jobs de otro run → `fail`. (3) Si el id del candidato es texto, decimal, NaN, ausente o mayor que 2^53, no se consulta la API y sale `fail`. (4) Si `listJobs` lanza → `fail`. (5) Un candidato con `created_at` futuro → no se piden jobs y sale `fail`. También se comprueba que `pickWorkflowCandidate` no reordena el arreglo de entrada.
- `listJobs` con fetch simulado: un id no numérico se reduce a `Number()` en la ruta, sin inyección de ruta. Con un `total_count` enorme, texto, negativo, decimal o ausente y todas las páginas llenas, nunca pasa de 5 páginas. Con 250 jobs pide 3 páginas. Si la página trae jobs con otra forma, un 404 o una lista, devuelve `[]` y el check da `fail`. Un `total_count` hostil que trunca la lista nunca produce un `ok` falso: quitar jobs solo puede quitar apariciones no omitidas, así que el resultado queda en `fail`.

Hallazgos:
- H-F19-01 · Info · 5 · `scripts/health/lib.js` (`requiredStepProblem`). Un job sin `run_id` se acepta. Para reproducirlo: `assessWorkflow(ritmo-diario, { runs: [success id 5], jobs: [{ steps: [{ name: 'Evaluar', conclusion: 'success' }] }] })` da `ok`. Corrección: exigir que cada job tenga un `run_id` entero igual a `candidate.id`. Requiere controlar la API de GitHub.
- H-F19-02 · Info · 5 · `scripts/health/lib.js` (`requiredStepProblem`). Una conclusión del paso `failure`, `null` o ausente cuenta como paso ejecutado y da `ok`. Hoy GitHub no puede dar ese caso con un run en success, porque los pasos no llevan `continue-on-error`. Corrección: exigir al menos una aparición con `conclusion === 'success'`.
