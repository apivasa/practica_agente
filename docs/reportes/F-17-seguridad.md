Hallazgos:
- **H-F17-01 · Info · 5** · `scripts/health/lib.js` (`compareSameTime`, rama de ids enteros). Si dos completados empatan en `created_at` y tienen el **mismo** id entero, el comparador devuelve 0 y decide el orden de entrada: `[success id 5, failure id 5]` da `ok` y al revés da `fail`. Para reproducirlo, llamar a `assessDeploy` con esos dos runs en los dos órdenes. GitHub no repite ids, así que no es explotable sin controlar la API. Corrección sugerida: cuando la diferencia de ids es 0, aplicar el mismo criterio fail-closed (el no-success va primero).
- **H-F17-02 · Baja · 5** · `scripts/health/lib.js` (`assessWorkflow`). Es anterior a F-17 y el ítem no lo empeora. `assessWorkflow` sigue ordenando los runs y midiendo la edad del candidato con `Date.parse`, sin `parseApiTime`. Un success con `created_at` en el año 2099 o ilegible pasa a ser el candidato y la edad sale negativa o NaN, así que no salta `maxAgeHours`. Resultado: `seguridad-semanal` da `ok` aunque el run real más reciente haya fallado. Con una fecha ilegible el comparador devuelve NaN y el resultado depende del orden de entrada. También se reproduce el problema de empate ya resuelto en despliegue: `ci-main` con `[success id 1, failure id 2]` y el mismo `created_at` da `ok`. Necesita controlar la API de GitHub. Corrección sugerida: usar en `assessWorkflow` `parseApiTime` para cada run (un completado con fecha inválida da `fail`) y `compareSameTime` para desempatar. Propuesto como ítem en `docs/seguridad/hallazgos.md`.
