## Hallazgos (ninguno bloqueante)
1. **Baja. Cuando otro miembro del comité edita una excepción, el aprobador queda sobrescrito.** `exceptions_update` exige `approved_by = auth.uid()` en el `with check`. Si el miembro B del comité quiere extender una excepción que aprobó A, solo puede hacerlo poniendo `approved_by = B`, así que se pierde quién la aprobó (solo queda en `audit_log`). Para reproducir: hay que tener dos usuarios `committee`; B ejecuta `update exceptions set expires_on=… where id=<de A>` y recibe 42501, o lo logra solo si cambia `approved_by`.
2. **Baja. Al actualizar no se protege `created_by`.** Las políticas `measurements_update` y `commitments_update` solo validan el indicador. Un custodio puede cambiar `created_by` (y `unit_id`) de filas de su KPI y atribuírselas a otro usuario. Para reproducir: el custodio ejecuta `update measurements set created_by='<otro>' where id=<suya>` y el cambio se aplica.
3. **Baja/media. Los borrados en cascada sin auditoría pueden borrar el historial de escalada.** Si la gestora borra una unidad o un indicador, `on delete cascade` elimina sus mediciones, evaluaciones, excepciones y alertas. Las tablas `units`, `measurements` y `evaluations` no tienen trigger de auditoría. El diseño dice "Evaluaciones: historial para la escalada". Sugerencias: usar `restrict` o desactivar (`active=false`) en lugar de borrar, o auditar `units`.
4. **Baja. Hay dos fuentes de verdad para líder y custodio.** `units.leader_user_id` e `indicators.custodian_user_id` pueden no coincidir con `user_roles`, que es lo único que usa RLS.
5. **Informativo.** Se puede crear una excepción con `expires_on` en el pasado; ningún check lo impide.
